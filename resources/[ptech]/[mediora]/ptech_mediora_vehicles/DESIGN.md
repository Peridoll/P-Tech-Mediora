# P-Tech Mediora Vehicles 設計書

更新日: 2026-10-30  
状態: 認識合わせ中・未コミット

## 1. 目的

EMS車両の運用機能と、今後追加する車両共通機能をひとつのFiveMリソースにまとめる。車両ごとの追加機能や車両データは個別フォルダに分け、車両が増えても共通処理と混ざらない構成にする。

## 2. リソース構成

リソース名は `ptech_mediora_vehicles`。

```text
ptech_mediora_vehicles/
├── main/                       # 全車両共通の処理
├── assets/
│   └── ptech_ems_blazer/       # EMS Blazer Aqua固有の設定・データ
├── config.lua                  # 共通設定
├── fxmanifest.lua
└── DESIGN.md
```

- 車両ごとに別のFiveMリソースは作らない。
- 共通処理は `main` に置く。
- 車両固有の設定・メタデータ・ストリームファイルは `assets/<車両ID>` に置く。
- 車両IDは衝突しないよう `ptech_ems_blazer` とする。
- ゲーム内スポーン名は、以前決めた `pemsblazer` を維持する。

## 3. Mecaniteから移すブレイザー機能

| 機能 | 仕様 |
|---|---|
| 専用車両 | EMS向け水陸両用ブレイザー `pemsblazer`。標準 `blazer5` は変更しない。 |
| 武器抑止 | 登録したブレイザーの運転席だけ武器を抑止する。 |
| 水上係留 | 無人・水上・低速時に横流れを弱める。車両を固定せず、衝突や押し出しを検知したら減衰を解除する。 |
| 降車直後の慣性 | 降車後に残る水平速度を短時間減衰させる。 |
| エンジン | 無人係留中に車両が停止したらエンジンを止める。 |
| GPS | 鍵を持つプレイヤーに対象緊急車両の位置を表示する。対象車両に乗っている間は、その車両自身のブリップを隠す。 |

係留では位置固定、衝突無効化、無敵化、元位置へのワープを行わない。OneSyncを含む実サーバーでの物理確認は未実施。

## 4. 車両後部からの呼び出し

- 呼び出し処理は共通機能として `main` に置く。
- 呼び出し可能な車両と搬送元車両の組み合わせは、呼び出す車両側の `assets/<車両ID>/config.lua` に登録する。
- 登録数が0台なら、共通の後部呼び出し機能を有効化しない。
- 登録が1台以上なら、登録済みの組み合わせだけを後部ターゲットに出す。
- 初期登録は「救急車 `ambulance` の後部から `pemsblazer` を展開・格納」。
- 展開時は操作したプレイヤーにブレイザーの鍵を付与する。
- 格納時は、元の出庫者に限定せず、救急車の鍵を持つプレイヤーが操作できる設計を目指す。
- プレイヤーが乗っている車両は格納しない。

展開位置・向き、破損車両の格納可否、搬送元車両が消失した時の扱いは実機確認または追加決定が必要。

## 5. 鍵

### 5.1 目指す挙動

- EMS車両の鍵はEMS内で共有して運用する。
- 運転席に乗った時に、その車両の鍵を自動取得できるようにする。
- 鍵を持つプレイヤーだけが、車両後部からブレイザーを展開・格納できる。

### 5.2 現在の実装仮定

作業フォルダの仮実装では、`ambulance`職かつ勤務中のプレイヤーに限定して、登録車両の運転席に入った時に鍵を付与する。これは安全側に置いた実装条件で、勤務外のEMSや別職の扱い、降車後の鍵の保持期間は最終確認が必要。

## 6. 車両管理・記録

車両ごとの作業履歴として、少なくとも次の記録を検討する。

- ガレージから出庫したプレイヤー
- 走行距離または運転時間
- 給油したプレイヤーと給油量
- 修理したプレイヤーと修理内容
- 各記録の対象車両と発生時刻

修理・給油については「作業をした人」を記録するのか、「作業時点で鍵を持っていた人」を記録するのかを分けて確定する。車両キーの共有状態を取得する方法と、ガレージ・給油・修理リソースのイベント接続も確認が必要。

### 6.1 Core連携とランキング

- 活動データの受信・集計・ランキングはMediora Core側が担当する。
- Vehicles側は、運転・給油など担当する活動の実績をCoreへ送る。
- 治療実績はMedical側から送る。
- Coreには現ポイント残高、総獲得ポイント、勤務時間合計、活動ごとの実績件数を集約する構想がある。
- 候補として「一番運転した人」「一番給油した人」「一番治療した人」が挙がっている。
- Coreへのイベント名、ペイロード、ポイント付与条件はまだ合意されていないため、この設計書では定義しない。

## 8. 依存関係・外部連携

現在の作業フォルダでは `ox_lib`、`ox_target`、`qbx_vehiclekeys`、`qbx_core` を利用する想定。サーバーのスクリプト台帳にはガレージ `jg-advancedgarages`、給油 `lc_fuel` の記録があるが、実稼働バージョンと拡張イベントは未確認。

外部リソースの内部イベントを推測して接続しない。ガレージ出庫記録、給油・修理記録、ショップ、費用割引、Core送信は、実際のAPIを確認してから接続する。
