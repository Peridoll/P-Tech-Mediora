# Rescue 開発状況

## 緊急離脱の利用設定

EMSタブレットの「設定」で管理者がPDとPD以外の有効・無効と待機時間（分）を保存できる。初期値はPDのみ有効、両方5分。CoreのサーバーKVPへ保存し、Rescueはサーバーで職業・ダウン状態・待機時間を確認してから搬送する。勤務状態による追加制限は設けていない。旧検証コマンドの登録を削除した。FiveM実機未検証。

## ローカルヘリ搬送テスト

開始時に暗転し、専用ルーティングバケットへ移動してからローカルヘリで最大60秒飛行する。病院ヘリポート以上の高度で水平45m以内に入るか、60秒に達したら到着処理へ進む。再度暗転して病院入口 (302.4, -585.78, 42.27) に移動し、元のバケットへ戻す。中断時は可能なら元の位置とバケットへ戻す。FiveM実機未検証。

## 搭乗テストのネットワーク同期

試験機を Maverick に変更。従来の Buzzard2 は検証環境の Qbox エンティティ禁止リストに含まれていた。配信の再試験は未実施。

ヘリとNPCをOneSyncサーバーで生成し、搭乗者と同じルーティングバケットに配置する。搭乗者は両方のネットワークIDと制御権を取得してから搭乗・飛行を開始する。帰還後はサーバーへ片付けを通知し、準備中断や切断時もサーバーが削除する。周囲のクライアントからの表示はFiveM実機未検証。

## 搭乗テストの飛行先

搭乗確認後、NPC操縦士に設定済みの病院ヘリポート（Config.Hospital.Helipad）へ向かうよう指示する。搭乗から5秒後に元の位置へ戻し、ヘリとNPCを削除する。FiveM実機未検証。

## 0.3.0 の実装

- manifestからルートの `config.lua` を読み込むよう修正。
- Coreの共通アクションパネルへ直接接続。Coreの停止時はテキスト表示、再起動時はパネルを再登録。
- Qboxの職業・勤務状態とWasabi/Qboxの死亡・瀕死状態を使用。クライアントもmetadataを参照。
- 要請受理後の資格継続はサーバーの250ms監視とphase検証に統一。クライアントの職業・死亡metadata・プレイヤーデータが一時的に未同期でも、受理済み要請を独自判定で破棄しない。サーバーが返すcitizenidと現在のped・確定したキャラクター変更はクライアントでも照合する。
- サーバー取消理由をクライアントへ送信し、受信待ち・制御取得・搭乗・飛行中の中断理由を赤いパネルに4秒間保持。ヘリ消失・操縦士消失・死亡状態終了・勤務終了・実体やバケット変更をログで区別する。
- 待機時間をサーバーで計測し、キャラクター・ped・バケット変更時には死亡セッションを破棄。
- ACE権限付き `/rescueskip [ID]` で対象の現在の待機時間だけをスキップ。ID省略時は自分、コンソールではID必須。使用済み・要請中は解除しない。
- Coreのチャット候補・`/mediorahelp` に時短コマンドを登録。実行権限とRescueの起動状態で表示を制御し、Rescueの起動・停止時にも候補を更新。
- 状態同期と毎フレームの長押し入力を別スレッドに分離。RPC前後の時刻差で待機時間が復活するリセットを修正。短い通信失敗では長押しを維持する。
- 死亡中に標準リロード入力が取得できない場合に備え、`lib.addKeybind` によるRescue専用の押下・解放状態へ変更。初期キーは `Config.Key`、表示は実際の割り当てに追従。長押し中は％を表示して共通パネルを一時展開し、サーバー応答待ちの前に要請送信中へ切り替える。ポーズメニュー・入力を占有するNUIに移った場合は保持を解除する。
- 状態取得が5秒または同期周期の3倍を超えて途絶えた場合は資格表示を破棄。サーバーが明示的に資格なし・使用済みを返した場合は即時反映し、要請前の古い応答は搬送後へ適用しない。
- 機体生成前の予約と要請ticketで重複生成・古い完了通知を防止。
- 長押し完了後の要請callbackも表示スレッドから分離。`Config.RequestTimeout`（標準15秒）で応答待ちを終了し、要請IDが一致する未搭乗機体だけを取り消す。遅れて返った古い成功応答は搬送を開始せず機体を回収する。
- サーバーの資格・待機・使用済み・機体生成の失敗理由を画面へ返し、赤いパネルに4秒間表示。失敗後はキーを一度離さないと再送しない。クライアントの送信・応答とサーバーの受理・生成完了をログへ記録。
- 生成された機体・パイロットの存在確認、生成例外の後片付け、搭乗前失敗時の再要請。
- ネットワーク制御取得、屋根高度補正、ローター・NPCパイロット初期化、回収中の機体固定。
- ローカルへ配信済みかを確認してからネットワークIDを解決。遠方の他人の機体や配信待ちの機体で `GetNetworkObject: no object by ID` を繰り返さないよう修正。
- 生成直後にヘリ・操縦士を固定。先にクライアントへ届いた方も制御取得後に固定し、同期を待つ間の落下を抑止。操縦士の搭乗前・飛行開始時に固定を解除。
- 配信待ちをヘリ・操縦士別に表示し、10秒で取得できなければ再要請を案内。配信タイムアウト・制御取得失敗・操縦士搭乗失敗時はF8へticket、ネットワークID、ローカルハンドルを出力。
- サーバーの座席・病院周辺座標の同期を待つ搭乗・到着callback。EMS通知は同じバケットの勤務中職員に各段階1回。
- 搬送中の蘇生・機体消失・タイムアウト・切断・停止の監視と後片付け。
- 失敗時の回収前位置への復帰。機体消失後は直前の機体位置から15m以内で他の車両に乗っていない同一患者だけを対象とする。

HP・死亡state・蘇生イベントは書き換えません。病院への最終配置はヘリがヘリポートから水平50m以内、患者が搬送機に搭乗中の場合に限ります。着陸に失敗してもこの範囲に留まっている場合は入口へ配置します。到着通知の確認に失敗した場合は入口に留まり、EMSへ直接連絡するよう案内します。

## 自動テスト

PythonとLua 5.4実行用のlupaを使用します。リポジトリのルートから実行します。

```powershell
python -m pip install -r 'resources\[ptech]\[mediora]\ptech_mediora_rescue\dev\tests\requirements.txt'
python -m unittest discover -s 'resources\[ptech]\[mediora]\ptech_mediora_rescue\dev\tests' -p 'test_*.py' -v
```

FiveM APIを模擬し、実際のサーバー・クライアントLuaを実行します。manifestの参照先と全Luaの構文、資格・待機時間、生成中の競合、世代違いの通知、搭乗と到着の検証、通知先・重複、失敗時の復帰、機体公開、Core再起動を検証します。状態取得の遅延・失敗と入力の切り替わりを模擬し、3秒長押し・途中のキー解放・古い応答の破棄も確認します。GTAの物理、AI、OneSyncの実際の所有権移行・通信遅延は再現しません。

## 実機での確認順序

1. 導入先の職業名と病院座標を設定し、依存リソースを先に起動。manifest・Luaのエラーがないことを確認。
2. 勤務中PDの死亡・瀕死でカウントダウンを確認。時短検証ではACE権限 `command.rescueskip` を持つ管理者で `/rescueskip [ID]` を実行し、R長押しが通信のたびにリセットされず3秒で完了すること、途中で離すと最初からになることを確認。権限なしでは実行不可、勤務外・他職・生存中・使用済みの対象はスキップ不可。
3. 屋外、屋内、地下、車内、水中で回収を確認。蘇生やHP回復が発生しないことを確認。
4. NPCパイロットの搭乗、飛行、停止時の指示再発行、ヘリポート接近・着陸・入口配置を確認。Wasabiが死亡者を座席から強制的に降ろさないか確認。
5. 同じバケットの勤務中EMSだけに開始・到着通知が各1回届くことを確認。
6. 複数クライアントで、本人の半透明表示・20秒後の公開・他人の機体への衝突抑止を確認。
7. 要請直後の蘇生、搬送中の蘇生・機体消失・通信遅延・バケット変更・切断・リソース停止を確認。失敗時の復帰先と機体削除を確認。
8. Coreの停止・再起動、Marineを起動しない構成、Marineとのパネル併用を確認。

ロープ演出と実機検証は引き続き未完了です。
